# KlovPlay design

This document covers how KlovPlay delivers results in real time without losing or double-counting them, and where the implementation departs from the original specification.

## Components

| Component | Tech | Role |
| --- | --- | --- |
| `crates/schema` | Rust, serde, ts-rs | The one definition of the wire contract: telemetry events, live diffs, REST models. `cargo test` exports TypeScript bindings to the reporter and the dashboard. |
| `crates/server` | Rust, axum, tokio, sqlx 0.9, aws-sdk-s3 | Ingestion, persistence, analytics API, SSE fan-out, dashboard hosting. |
| `migrations/` | PostgreSQL 13+ | Schema, applied on startup. |
| `packages/playwright-reporter` | TypeScript | Implements Playwright's `Reporter`; batches events and uploads artifacts. |
| `apps/web` | React 19, Vite, Tailwind, TanStack Query/Virtual | Dashboard, plus Playwright's trace viewer copied from `playwright-core`. |

## Data flow

1. **Launch handshake.** `onBegin` posts `LAUNCH_INIT` (project, `ci_run_id`, shard i/n, planned test count). The server upserts the launch on `(project, ci_run_id)` and the shard on `(launch, shard_index)`, so every shard of a CI run lands in one launch. Playwright does not await `onBegin`, so this request runs in the background and queued events wait for the launch id.
2. **Events.** Test start, step start/end and test end are queued in memory and sent in ordered batches: every 300 ms or at 100 events, one request in flight at a time.
3. **Ingestion.** The handler checks the API key, and that every referenced launch belongs to that key's project. It then reserves room for the whole batch in a bounded channel (50 000 events) and waits.
4. **Flusher.** A background task drains up to 250 events, or whatever arrived within 200 ms. It writes them in one transaction using set-based statements (`jsonb_to_recordset`), commits, and only then acknowledges the requests whose events were in it.
5. **Live diffs.** After commit, the flusher publishes diffs to the launch's broadcast channel: test rows, worker activity, counters and completion. Each SSE connection forwards them. Rows are only re-read from the database when someone is watching that launch.
6. **Artifacts.** When a test ends, its result is queued immediately. In the background the reporter waits until that test's `TEST_START` is stored, asks for pre-signed PUT URLs, streams each file from disk to S3, and confirms with `/artifacts/complete`. The server checks the objects exist before marking them uploaded.
7. **Shard end.** `onEnd` waits for pending uploads and events, then sends `SHARD_END`. When every shard has ended, the launch is finalized: open attempts become `interrupted`, counters are final, and the status becomes passed, failed or interrupted.

## Delivery guarantees

| Concern | Mechanism |
| --- | --- |
| A crash must not lose acknowledged data | The HTTP response is sent only after the flusher's transaction commits. |
| Retries must not duplicate data | Execution, step and artifact ids are generated by the reporter. Inserts are `ON CONFLICT DO NOTHING`, updates are keyed by id, shard end is an upsert. |
| Counters must not drift | Counters are recomputed from the latest attempt of every test (throttled to 500 ms per launch), never incremented. |
| Events must stay in order | The reporter keeps one batch in flight; the channel is FIFO. Within a flush, statements run starts, then steps, then ends. |
| Overload | A request that does not fit in the channel gets `503` with `Retry-After`. The reporter backs off and keeps the batch at the head of its queue. |
| One bad request must not fail others | If a flush fails, its requests are retried one by one. Data errors (SQLSTATE 22/23) answer `422` and are dropped by the reporter; other errors answer `503`. |
| Reporter crash or killed CI job | Launches idle for `STALE_LAUNCH_MINUTES` are marked interrupted. Long, quiet tests stay alive through a 60 s heartbeat. |
| Tests must never fail because of reporting | Every reporter hook is non-throwing. If the server is unreachable, events are retried, then counted and reported as undelivered when the run ends. |

## Data model notes

- **One row per attempt.** `test_executions` holds each attempt. When retry *n* starts, earlier attempts of the same test are marked `superseded`. Counters, test lists and history read only non-superseded rows, so a test that passes on retry counts once, as flaky, and its earlier failure stops counting.
- **Flaky** is assigned on `TEST_END`: status `passed` with `retry_attempt > 0`. Expected failures (`test.fail()`) are reported as `passed` by the reporter, and unexpected passes as `failed`.
- **Fingerprint.** SHA-256 of `file::describe>path::title::project`, with the file path relative to Playwright's root directory. It links a test across launches on any machine.
- **Error cluster hash.** SHA-256 of the error after removing ANSI codes, Playwright's call log, UUIDs, timestamps, ports, memory addresses, absolute directories and long numbers, plus the first three `at` lines of the stack.
- **Steps** are rows linked to their parent, written as they start and end. In `steps-only` mode, a step's parent is its nearest reported ancestor, so nesting survives filtering.

## Live updates in the browser

`useLaunchStream` loads the launch and its tests over REST, opens the SSE stream, and refetches when the stream (re)connects. That closes any gap between the snapshot and the first diff. Diffs are buffered and applied once per animation frame, and test rows are upserted by Playwright test id so a retry replaces its earlier attempt. A client that falls behind the broadcast buffer is disconnected; `EventSource` reconnects and resyncs. Failure clusters are computed by the server and refreshed at most every 2 s during a run.

## Deviations from the original specification

| Specification | Implemented | Why |
| --- | --- | --- |
| MinIO (`minio/minio:latest` + `minio/mc` init) | RustFS 1.0.4 in Compose; the server creates the bucket and its CORS rule itself (`S3_ENSURE_BUCKET`) | MinIO no longer publishes community images or binaries (the image is gone from Docker Hub, and its binary download returns 410). Any S3 API works. |
| HTTP handler returns after enqueueing | Returns after the events are committed | Otherwise a restart loses events the reporter believes were delivered. |
| Counters incremented, flaky "decrements previous failures" | Counters recomputed; earlier attempts marked `superseded` | Retried batches would double-count increments. |
| `onBegin` makes a "synchronous" init request | Init runs in the background; events wait for it | Playwright does not await `onBegin`, and blocking the event loop would stall the runner. |
| Uploads read with `fs.readFile`, then TEST_END | TEST_END sent at once; files streamed to S3 in the background | Playwright does not await `onTestEnd` (checked in the 1.64.1 source), and traces and videos can be hundreds of MB. |
| `file_path` as given by Playwright | Relative to the Playwright root | Absolute paths differ between CI machines and would break history. |
| Retry command `-g "<titles>"` | `file:line --project=…` | `-g` is a regular expression and can match other tests. |
| `rust:1.94-slim` builder, `debian:bookworm-slim` runtime | `rust:1.94-slim-bookworm` builder | The builder's glibc must match the runtime's. |
| — (additions) | `launch_shards`, `parallel_index`, `superseded`, `error_snippet`, artifact `file_name`/`uploaded_at`, `last_event_at`; `ShardEnd.status`; optional `TestEnd.annotations` for labels added at runtime; heartbeat, project and launch list, analytics and history endpoints; `ArtifactUploaded` diff | These are needed for idempotency, stable worker lanes, the overview pages and runtime labels. |

## Scaling notes

- Ingestion cost is about one transaction per 250 events. A 50-shard × 8-worker run finishing around 40 tests per second is well within one server and one PostgreSQL instance. Throughput scales with `FLUSH_MAX_EVENTS` and the database.
- Artifact bytes never pass through the server.
- Step rows grow fastest. `stepMode: 'steps-only'` (the default) keeps them to `test.step()` calls.
- **One server instance today.** Live fan-out uses in-process broadcast channels. Running several replicas needs a shared bus (PostgreSQL `LISTEN/NOTIFY` is the natural next step), plus sticky routing until that lands.

## Roadmap

1. Multi-instance live fan-out (`LISTEN/NOTIFY`) and a project-level stream for the overview pages.
2. Authentication for the dashboard (OIDC), and per-project roles.
3. Retention: delete old launches and their S3 objects; partition `test_executions` and `test_steps` by month at high volume.
4. A Cmd+K palette with the existing search syntax (`status:`, `@tag`, `project:`, `owner:`).
5. Reporters for Playwright Java, Python and .NET, and an ExtentReports bridge, on the same HTTP contract.
6. A licence for this repository (the upstream Klov repository has none).
